# 2단계 · 화면 목업 검수

상태: 구현·기능/화면 검증 후 사용자 검수 대기. 다음 단계 승인은 아직 받지 않음.

최신 검수 대상은 UI/사용 흐름 피드백을 반영한 [통합 작업실 재설계](09-workflow-redesign.md)다. 메일 작업실(`/`), LLMOps 판단실(`/operations`), 실행 감독(`/supervision`)에서 업무 단위로 검수하고, 이전 상세 페이지는 심층 원장으로 사용한다.

2026-10-29 보강: 뎁스 2 상세 화면 8종과 검수 시나리오 10종을 추가하고 검증했다. 최신 검수 시작점은 `/scenarios`이며, [상세 화면·시나리오 가이드와 검증 기록](08-depth2-scenarios.md)을 따른다. 아래 2026-10-05 기록은 기본 화면의 이전 검증 기록이다.

## 확인할 화면

| 화면 | 검수 포인트 |
|---|---|
| 운영 개요 | 승인 대기와 품질 회귀가 먼저 보이는가? 업무 성공과 품질 합격을 구분하는가? |
| 메일 검토 | 목록 선택 → 원문/초안 비교 → 수정 저장 → 확인 후 승인/거절이 자연스러운가? |
| 실행 이력 | 계획, span 입출력/토큰/시도, 순서 있는 이벤트를 같은 실행에서 확인할 수 있는가? |
| 에이전트 | Supervisor와 전문 agent, 별도 Diagnose 역할, Registry 계약과 예산이 이해되는가? |
| Eval | 고정 dataset/evaluator/manifest, 기준·후보 점수, 실패 사례를 비교할 수 있는가? |
| Observe | 토큰·비용·지연·실행량을 선택하고 관측 기간을 바꿀 수 있는가? |
| Diagnose | 7개 건강 차원, 관찰과 원인 가설, 증거와 권고가 구분되는가? |
| 릴리스 판단 | 8개 게이트와 증거가 보이고 FAIL/UNKNOWN은 승격이 차단되는가? |
| 환경·연결 | 실제 미연동 상태와 보안 경계가 분명한가? |

## 직접 눌러볼 흐름

1. `/reviews`에서 첫 메일 초안을 수정하면 승인이 비활성화된다. ‘수정 저장’ 후 revision이 올라가고 승인이 가능해진다.
2. 승인 확인 모달에서 합성 Draft 저장을 실행한다. 실제 Gmail 저장/발송은 없다. 연결된 실행 이력에서 `draft.edited` / `draft.saved`를 확인한다.
3. 다른 대기 메일을 거절한다. 메일 검색에 없는 값을 넣으면 빈 상태가 나타난다.
4. `/runs`에서 실패 실행을 선택해 제한 재시도 종료와 오류 span을 확인한다. 이벤트의 span ID를 클릭하면 해당 입출력으로 이동한다.
5. `/evaluations`에서 실패 사례 ‘검토’를 눌러 기대/결과를 비교하고, Diagnose와 릴리스 게이트를 따라간다.
6. `/releases`에서 r0.2.1은 개선 필요, r0.2.2는 근거 부족으로 차단된다. r0.2.0은 모든 게이트 통과 후 확인 모달로 합성 canary 승격이 가능하다.
7. ‘테스트 실행’으로 합성 실행을 추가한다. 실제 메일을 조회하지 않는다.
8. `/?scenario=error`에서 통신 오류 상태와 ‘다시 시도’ 복구를 확인한다.

## 재사용과 검증 범위

라우트, DTO, UI 컴포넌트, CSS 토큰은 실제 구현에 재사용한다. `VITE_DATA_MODE=api`에서 MSW를 끄고 동일 `/api/v1` 호출을 백엔드로 연결한다. 브라우저 화면 파일을 새로 만드는 방식이 아니다.

검증: production 빌드/TypeScript, Playwright 사용자 흐름, 1440px / 1024px / 390px / 320px에서 9개 화면 캡처와 페이지 가로 overflow 점검. 화면 이미지는 `frontend/test-results/screens`에 생성된다. 테스트 결과는 `frontend/playwright-report`에 생성된다. 모달 Escape/원래 버튼 포커스 복귀, 조회 오류 복구, fixture schema/토큰 중복 집계 방지/이벤트 span 상관도 시험한다.

UI 스킬의 작업 중심 구성·필수 상태·반응형·실렌더 검증 기준을 적용했다. UIZZE 참고 서비스에 접근하지 못해 외부 화면 관찰을 주장하지 않는다. 대비와 레이아웃은 직접 캡처를 확인해 조정했다. 자동 테스트는 mock의 revision/gate 거부를 확인하지만 실제 서버 인증·보안 검증은 아직 수행하지 않았다.

최종 검증 기록 (2026-10-05):

- `npm run build`: 통과. TypeScript + production bundle, 500KB 초과 chunk 경고는 분할 후 해소.
- `npm run test:e2e`: **8 passed**. 4개 viewport × 9개 화면 = 36개 캡처, 페이지 가로 overflow 없음, 해당 탐색 중 uncaught JavaScript 오류 0.
- 메일 수정/저장/revision/승인/거절, 이벤트 연결, 빈 검색, Eval 사례, 테스트 실행, Observe 선택, 모달 Escape/포커스 복귀, API mock의 stale revision / gate 차단, 오류 복구 통과.
- 초기에 발견한 모달 포커스 복귀 문제 수정 후 전체 테스트를 다시 실행해 통과.

개발 서버는 `http://127.0.0.1:5173/`에서 실행한다. 다른 환경에서 테스트하려면 Chrome 실행 경로를 설정해야 한다.

## 아직 실제로 동작하지 않는 것

- Gmail OAuth/검색/Draft, Hermes Gateway, 실제 LLM 호출, LangSmith trace/eval 전송, SSE, DB 영속화
- 실제 holdout 300건, staging 248건, 지연·토큰·비용 측정: 모두 화면용 합성 값
- 운영 배포와 rollback: 승인 후 별도 구현·검증 필요
- API 모드: 백엔드를 구현하기 전에는 통신 오류 화면이 정상 결과다.

3단계에서는 공급자/모델과 비용, Hermes 제품 버전, Gmail 테스트 계정, LangSmith 개인정보 정책을 확정한다. 이 설정은 서버 계약 경계 안에서 연결하므로 화면 재설계를 요구하지 않는다. 보안·성능 검증에서 필요한 수정은 사용자와 변경 사유를 공유한다.

검수 후 수정 의견 또는 ‘목업 승인’을 요청한다. 승인 전에는 Tool 연동을 시작하지 않는다.
